# Composable extractors and code surgery

Implementation plan for BootLoops, based on `ftqc_integration` at `9b5952e`. The first deliverable is a checked joint Pauli measurement whose output can drive another operation on surviving logical qubits. Once two independently constructed implementations can pass the same consumer, add optimizations for ancilla count, parallelism and measurement time. The success criterion is replay of a combined physical schedule, including the faults at the handoff.

## Where the surgery code belongs

**Put a reusable logical measurement in `ftqc_gadgets` and an installed collection of such measurements in `ftqc_extractors`.** A caller with a code, a signed Pauli and two candidate merge–measure–split circuits should be able to construct, check and compare both through Gadgets alone. A caller asking whether one fixed apparatus covers a set of Paulis, which bridges can coexist, or how quickly a program can use them needs Extractors.

| Owner | Work and public result |
|---|---|
| `ftqc_gadgets` | Own the finite surgery instance, its constructor, ideal measurement instrument, per-operation schedule, incoming-error and internal-fault accounting, and refinement against a reference instrument. Put generic pushouts, homological and gauging gadgets, parsimonious ancillas, adapters and multi-parity gadget constructors here. A parallel gadget can have several public bits. |
| `ftqc_extractors` | Generate architecture-specific HGP or lifted families, select verified gadget instances, install physical ports on named blocks, certify partial or full coverage, schedule shared boundaries and track PBC feed-forward. Delegate an isolated operation to Gadgets. Return an architecture or sequence receipt binding each checked gadget to its physical placement. |
| `ftqc_compose` | Consume a replayed instrument contract directly from Gadgets for a standalone operation, or consume the additional placement and schedule evidence from Extractors for an assembled program. Check residual filters and conditional premises at the join. |

For example, a universal repetition adapter between two abstract blocks belongs in Gadgets. The matching that embeds that adapter into two installed blocks belongs in Extractors. The proof that the surviving encoded output meets the next consumer’s error tolerance belongs in Compose. A lifted gadget’s binary matrices can pass to Gadgets even when Extractors used cyclic orbits to choose them. Keep dependencies one-way for new code. Gadgets takes explicit code, maps and schedules and can use Codes and Faults directly. Its checker must run with no extractor layout, PBC compiler or Compose import.

## The interface between construction and verification

Add a versioned surgery measurement instrument and receipt to the Gadgets CLI. Its current `analyze --check` supports prep, gate and EC properties. A measurement has stochastic ideal outcomes, conditional postmeasurement data and public records. Introduce a measurement property with those semantics in the Gadgets analysis, property and receipt-verification paths. Build its reference by projecting the encoded Bell-input experiment onto each public outcome and applying the declared split correction. Allow private outcomes to be marginalized. Preserve the existing convention that incoming Pauli weight and internal faulty locations have separate budgets. [Gadget semantics](../tools/ftqc_gadgets/GUIDE.md)

At the architecture layer, extend the existing schema-1 `ftqc_extractors check SPEC -o RECEIPT` and `verify SPEC RECEIPT` dispatch with additive input kinds for installed settings. Bind both the gadget input and its verified receipt, the local-to-global placement, any extra gates and the schedule. Recheck conflicts after placement and re-audit any altered circuit. A constructor emits an explicit finite instance which a verifier can check without rerunning a heuristic or trusting a library’s distance label. Keep legacy inputs and receipt verification as regression fixtures. Introduce the shared representation first through two existing examples. Add fields when a second construction or consumer exercises them.

| Boundary | Evidence to carry and check |
|---|---|
| Logical request | Ordered memory blocks, check generators and signs, paired logical X/Z representatives, signed target Paulis, returned bits, requested joint subgroup, and named surviving pairs. Reduce targets modulo stabilizers including phases. Check commutation, independence or declared dependencies, and that the apparatus reveals exactly the requested subgroup. In a joint parity measurement, reading each factor separately leaks logical information. |
| Construction | Auxiliary qubits, checks and gauge choices, port maps, physical IDs, merge and split rules, classical outcome parity and branch-dependent output frame. Recompute commutation, ranks, quotient maps and spectator action over the complete surviving logical algebra. A mixed Pauli needs a signed symplectic representation or a checked basis change and its inverse. |
| Execution | Record physical preparations, disjoint gate layers, idles, resets, measurement records, detector and observable maps, feed-forward ordering and boundary conditions. Specify qubit reuse and every noisy location. Distinguish physical ancillas, check meters, installed couplers, peak live qubits, syndrome rounds and gate depth. |
| Claim | Bind the source version, input matrices, settings, schedule and decoder configuration to replayable evidence. Keep static code distance, phenomenological distance, circuit fault distance, decoder guarantee and sampled error rate as distinct claims. Record proven lower bound, witnessed upper bound, or unresolved obligation. A failed expansion test blocks that theorem. A physical counterexample requires a fault set and a damaging output. |
| Composition | Produce classical measurement bits plus the ordered post-split quantum outputs, signed frame, acceptance rule and residual-error filter. Reuse the existing port keys and `contracts.join`. Verify any change of basis or wire permutation explicitly. Track shared randomness, correlated faults and conditioned acceptance across consumers. A closed contract must discharge every premise within its stated scope. |

## Implementation order and acceptance tests

### 1. Prove one end-to-end measurement on existing fixtures

Implement the standalone instrument in Gadgets first. Use the Extractors fixture `examples/edge-extractor.json`, its `edge-hook.json` mutation and the existing `ftqc_compose/hgp.py` leaf. Export the signed result and split frame into a second measurement of a surviving logical. For a tiny code, enumerate ideal branches with a reference entangled to the surviving input. Compare the composed instrument with the direct two-measurement specification. Replay the known circuit-distance-two result and the one-location spectator hook. Delete a frame column, reverse a logical pair, and change the identity of a record bit. Each affected consumer must detect the error.

Migrate incrementally. First export the existing extractor fixture into a self-contained Gadgets input. Run its verifier independently on the export and compare signed outcomes, spectators, incoming-error responses and internal fault witnesses on the shared scope. Next make new extractor settings consume that Gadgets receipt. Factor out a legacy checker only after archived extractor specs and receipts replay with their original CLI and semantics. Register passing and hook controls in both native suites.

Implement the first compose exporter only for the existing accepted diagonal-Pauli scope. For an X/Z-conjugate or adaptive quantum sequence beyond that scope, use signed instrument replay on the enclosing schedule. Extend the formal compose scope in its own milestone with explicit semantics and tests. Give both paths a shared fixture so they must agree on their overlap. [Contract rules](../tools/ftqc_compose/contracts.py) · [HGP bridge](../tools/ftqc_extractors/AUDIT.md)

### 2. Build interchangeable single-observable constructors

In Gadgets, start with an explicit CSS merge/split from Cohen et al. and the chain-complex pushout of Cowtan and Burton. Use a small surface-code merge as an orientation and parity reference. Implement edge-expanded homological measurement from Ide et al. and graph gauging from Williamson and Yoder as separate producers. For the former, derive the mapping cone from the chain map and check the expansion and distance hypotheses. For the latter, derive the deformed checks from the graph, check connectivity, cycle constraints and port expansion, then recover the target from the measured checks. Add signed non-CSS support after the CSS intersection passes. Accept SSIP-generated matrices as an optional reference input with recorded provenance. [Lattice surgery](https://arxiv.org/abs/1111.4022) · [Generalized surgery](https://arxiv.org/abs/2110.10794) · [CSS pushouts](https://arxiv.org/abs/2301.13738) · [SSIP](https://arxiv.org/abs/2407.09423) · [Homological measurement](https://arxiv.org/abs/2410.02753) · [Gauging](https://arxiv.org/abs/2410.02213)

**Exit test.** Measure the same signed parity on the same small CSS block with both graph and homological constructors. Compare projected data subgroups, branch probabilities and corrected spectator actions after summing out private gauge records. Use exhaustive static distance on the small example. Save separate circuits and witnesses for each construction. Break a cycle generator and test a sign-flipped mixed-Pauli target.

### 3. Combine smaller ancillas with parallel and cross-block readings

In Gadgets, implement Cross et al.’s bridging construction and Swaroop et al.’s repetition adapter, including the sparse change of check basis. In Extractors, install the resulting gadgets through the existing matching bridge wherever its hypotheses suffice. Add Cowtan et al.’s branching procedure to obtain disjoint physical representatives for logically disjoint products. Implement Yuan et al.’s parsimonious coning as an alternative ancilla constructor. Export the transformed checks, port embeddings and cycle relations so the verifier can independently recover the original parity. The paper’s single-operator bound is O(W log W) for physical representative weight W. Measure the actual finite ancilla cost after adapters and branching. [Bridging codes](https://arxiv.org/abs/2407.18393) · [Universal adapters](https://arxiv.org/abs/2410.03628) · [Parallel measurements](https://arxiv.org/abs/2503.05003) · [Parsimonious surgery](https://arxiv.org/abs/2603.05082)

**Exit test.** On two small blocks with different CSS check matrices, measure two independent joint parities whose starting representatives share physical support. Compare a serial reference, parallel branched construction and parsimonious variant against the same requested subgroup. Count the installed couplers and peak live meters, check for extra leakage and simulate a follow-on spectator read. Reject a port permutation that swaps the two output bits and a parallel schedule that reuses a meter in one layer. Any change to a graph invalidates its cached distance and schedule evidence.

### 4. Exploit code structure and time amortization

| Construction and priority | Finite implementation and gate for adoption |
|---|---|
| **First, padded HGP sequences.** Use Chang et al.’s compact construction with the existing Cowtan et al. sequence checker. | Generate the auxiliary maps and a family of successive HGP settings. Compare standalone and amortized cost including the initial and final rounds once per run. Shorten one boundary and verify that the sequence guarantee is withdrawn. [HGP surgery](https://arxiv.org/abs/2603.02157) · [Sequence checker](../tools/ftqc_extractors/surgery_sequence.py) |
| **Next, lifted and canonical extractors.** Berent et al. supply a one-round, same-Pauli-type radial-code example. Zheng et al. organize reusable seed surgeries by cyclic logical orbits. | Expand the group-algebra data into explicit binary matrices and check the chosen basis, logical independence, orbit action and seed wiring. Target the published 90-qubit radial instance after a brute-force toy lift. Compare its one-round circuit with repeated ordinary surgery using identical boundaries and noise. Separately replay a canonical lift through two translated seed settings on one installed graph. Treat the two families’ hypotheses independently. [Lifted surgery](https://arxiv.org/abs/2609.11723) · [Canonical lifted products](https://arxiv.org/abs/2607.28605) |
| **Then, high-rate parallel gadgets.** Cowtan and Ide use linear probabilistically checkable proofs of proximity (PCPPs) to construct sparse auxiliary systems. | Start with explicit small verifier matrices, proof coordinates, the subcode embedding and a deterministic finite check of relative cosystolic expansion. Record subcode support size, measured rank, sparsity and auxiliary size. Test the phenomenological distance target with the prescribed d rounds. Defer general PCPP generation until a finite instance passes and yields a useful size at matched measured rank. [High-rate surgery](https://arxiv.org/abs/2609.26973) |
| **Architecture-specific follow-ups.** Parallel product surgery and neutral-atom algebraic surgery supply different connectivity assumptions. | Add the QGPU product connection on a small HGP instance. For shuttling, supply coordinates, movement layers, collision rules and durations. Compare packed independent readings at fixed hardware and include transport in the time budget. [QGPU](https://arxiv.org/abs/2603.05398) · [Parallel algebraic surgery](https://arxiv.org/abs/2609.39874) |

### 5. Close the physical and operational claims

Use `ftqc_codes` for GF(2) algebra, base-code ancestry and finite distance evidence. Export the local schedule and detector and observable definitions from Gadgets to the audit engine of `ftqc_faults`. Extend the Extractors schedule exporter to remap those definitions and insert any additional idles, shared rounds or routing gates in the assembled study. Validate ideal instruments with its ZX engine where supported. Include stabilizer signs, acceptance and all surviving observables in the comparison. For each schedule, replay a lower-bound exclusion and a damaging witness where tractable. At larger sizes, report the interval reached at a fixed budget. [FTQC tool boundaries](../tools/FTQC.md)

Pass detector events, correlated alternatives at each location and the declared noise model to `ftqc_decoders`. Cross-check exact single-location signatures against an independent simulation. Exercise metacheck repair and compare modular decoding against a joint decoder where both apply. A detector-error model which approximates correlations needs a separate claim. Have the Gadgets measurement verifier certify its open-input residual guarantee against the actual scheduled implementation, covering admitted incoming errors and internal faults together. Teach `ftqc_compose` to verify that guarantee before accepting a general surgery leaf. Shared padding or a reused ancilla can couple neighboring leaves. Audit their joint schedule and give each physical location one identity. A stochastic composition additionally needs a joint noise hypothesis. Supply measured feedback latency to `ftqc_uncompute` only for a workload that actually uses measurement-based cleanup. [Decoder guide](../tools/ftqc_decoders/GUIDE.md) · [Gadget guide](../tools/ftqc_gadgets/GUIDE.md) · [Composition](../tools/ftqc_compose/GUIDE.md)

**Hardware reference.** Reconstruct Luthra and Owens’ two-logical-qubit bicycle-code experiment, including the seven-qubit gadget, the one- and three-round schedules, and the sequential X₁ then Z₂ setting with reused ancillas. Compare readout and spectator errors separately. Record the conditioning, shot counts and intervals of the published observations alongside simulated results. Mark any unreleased native scheduling or noise information as an input assumption. Use the BB144 gross-code fixture and the bicycle architecture for a larger circuit and compilation comparison. [Trapped-ion surgery](https://arxiv.org/abs/2610.39067) · [Tour de Gross](https://arxiv.org/abs/2506.03094)

## Combined demonstration and rollout

The first integrated benchmark should use a partial HGP extractor, an independently constructed cross-block adapter and a follow-on read of a surviving logical controlled by the first result. Enumerate both signs, compare the signed quantum instrument to the reference, and replay detector, residual and decoder evidence end to end. Repeat with the parsimonious ancilla substituted **only at the same logical and physical interface**. If it requires added couplers, publish a second hardware configuration and reprice it. For a larger BB144 or lifted-code study, publish target, attained evidence, premises, seed or proof, resource counts and search budget for each variant. Rank candidates by qubits and time only after matching logical task, connectivity, noise, boundaries and required strength of evidence.

Land milestones 1 and 2 first. Milestone 3 and the HGP work in 4 can then proceed independently. Introduce physical audits from milestone 5 with each new constructor. Require the combined demonstration before making an optimization available to the PBC compiler by default. Support old specs in the normal CLI, and replay positive, witnessed-negative, invalid and budget-limited cases with the existing exit conventions. Add the small tests to the registered suites. Keep full-scale circuit searches and sampled comparisons reproducible as separate studies. For each implementation merge, run from BootLoops:

```sh
python3 run_selftests.py ftqc_codes ftqc_extractors ftqc_decoders ftqc_gadgets ftqc_compose ftqc_uncompute
python3 run_selftests.py ftqc_faults ftqc_audit ftqc_zx
```

Replay the research checkout’s `studies/replay.sh` against the candidate pin, refresh the integration tip and rerun affected fixtures after merging. Publish the seeds and exact dependency versions used for optional solvers. An unavailable optional backend leaves its associated claim open.

## Future factory handoff

The future `ftqc_magic` producer and the extractor consumer need agreement on the encoded target state and sign, block and ordered slot, Pauli/Clifford frame, acceptance record, availability, quality metric and conditioning, joint errors across a batch, and the boundary at which preparation ends. The consumer supplies its signed injection or teleportation branches, encoder and transport assumptions, and per-branch residual guarantees. Composition would validate compatibility and account for shared fault sites, acceptance probability and retries. A marginal error rate alone cannot justify independent use of two outputs from one batch.

This roadmap reserves that discussion for the factory maintainers. All milestones above can use existing explicit resource premises and conditional logical-T fixtures. Factory schemas, imports, adapters and executable integration belong to a later joint change.
